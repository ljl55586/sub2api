# sub2api 源码同步、重新部署与压测运行手册

这份文档解决两个问题：

1. 本机修改了 sub2api 源码后，怎样安全同步到服务器并让新代码真正生效；
2. 本机修改了压测脚本、提示词或调度计划后，怎样同步到服务器并开始一轮全新的压测。

本文按“照着复制命令也不容易出错”的方式编写。每一步都说明：

- 在哪里执行；
- 这一步是做什么；
- 怎样判断成功；
- 出错时应该停在哪里。

---

## 0. 先记住这张流程图

```text
本机修改文件
    ↓
本机测试
    ↓
只暂存本次修改
    ↓
commit
    ↓
push 到 myfork
    ↓
服务器停止旧压测
    ↓
服务器从 myfork pull
    ↓
┌──────────────────────────────┐
│ 改了后端源码？               │
│                              │
│ 是 → build 镜像并重建容器    │
│ 否 → 不重启 sub2api          │
└──────────────────────────────┘
    ↓
服务器执行测试
    ↓
创建全新的压测输出目录
    ↓
启动 run_24h.sh
```

最重要的四条规则：

1. 不要使用 `git add .`，避免把密钥、抓包、图片或无关文件一起提交。
2. 服务器上还有旧压测时，不要直接拉取并覆盖脚本。
3. 只修改压测脚本时，不需要重新 build 或重启 sub2api。
4. 每次重新压测都必须使用新的 `SOAK_OUTPUT_DIR`，不能复用旧目录。

快速导航：

- 第 3～8 节：本机测试、commit 和 push；
- 第 9～12 节：服务器停止旧压测并 pull；
- 第 13～17 节：改了后端源码时重新 build 和部署；
- 第 18～20 节：只改压测脚本时的服务器操作；
- 第 21～32 节：设置 tmux 环境并开始正式压测；
- 第 33～43 节：运行中检查和常见故障；
- 第 44～46 节：最短命令清单和最终确认表。

## 2. 先判断自己改了哪一类文件

在本机执行：

```bash
cd /Users/ling/sub2api
git status --short
```

### 情况 A：改了 sub2api 后端源码

常见文件包括：

```text
backend/**/*.go
backend/go.mod
backend/go.sum
frontend/**
Dockerfile
```

这类修改同步到服务器后，通常需要：

1. 重新 build Docker 镜像；
2. 只重建 sub2api 应用容器；
3. 不重建 PostgreSQL 和 Redis。

### 情况 B：只改了压测脚本或压测材料

常见文件包括：

```text
docs/test/claude-oauth-soak-24h/*.sh
docs/test/claude-oauth-soak-24h/lib/**
docs/test/claude-oauth-soak-24h/sessions/**
docs/test/claude-oauth-soak-24h/prompts/**
docs/test/claude-oauth-soak-24h/followups.json
docs/test/claude-oauth-soak-24h/schedule.tsv
docs/test/claude-oauth-soak-24h/README.md
```

这类修改同步到服务器后：

- 不需要 build Docker 镜像；
- 不需要重启 sub2api；
- 需要停止旧 runner；
- 需要用全新的输出目录重新启动 runner。

### 情况 C：后端和压测脚本都改了

先按“后端源码流程”重新部署 sub2api，再按“压测脚本流程”执行检查并启动新压测。

### 情况 D：改了 Compose 或 `.env`

例如：

```text
deploy/docker-compose*.yml
/root/sub2api-deploy/docker-compose.yml
/root/sub2api-deploy/.env
```

这类修改一般不需要重新 build 镜像，但需要重新创建 sub2api 容器，让新环境变量进入容器。

如果同时改了 Go 源码，则仍然要先 build 镜像。

# 第一部分：本机如何提交并推送修改

## 3. 本机第一步：确认当前分支

在本机执行：

```bash
cd /Users/ling/sub2api
git branch --show-current
```

正常应该显示：

```text
codex/claude-request-alignment
```

这一步是为了防止把修改提交到错误分支。

如果显示的是别的分支，先不要继续。确认是不是自己故意换了分支。

---

## 4. 本机第二步：查看究竟修改了什么

执行：

```bash
git status --short
```

常见状态：

```text
 M file.go
?? new_file.go
```

含义：

- `M`：已有文件被修改；
- `??`：新增文件，还没有被 Git 跟踪；
- 没有输出：当前没有未提交修改。

再查看实际代码差异：

```bash
git diff
```

如果输出太长，可以分页查看：

```bash
git diff | less
```

在 `less` 中：

- 方向键或 PageUp/PageDown：上下移动；
- 按 `q`：退出。

这一步是为了确认没有误改密钥、抓包、日志或其他无关文件。

---

## 5. 本机第三步：按修改类型执行测试

### 5.1 如果改了 Go 后端

进入后端目录：

```bash
cd /Users/ling/sub2api/backend
```

只格式化自己改过的 Go 文件。例如：

```bash
gofmt -w \
  internal/service/gateway_claude_upstream_approval.go \
  internal/service/gateway_forward.go
```

然后运行相关服务包测试：

```bash
go test ./internal/service -count=1
```

成功标志类似：

```text
ok   github.com/Wei-Shaw/sub2api/internal/service
```

如果出现 `FAIL`：

- 不要提交；
- 不要同步到服务器；
- 先修复测试失败。

测试完成后回到仓库根目录：

```bash
cd /Users/ling/sub2api
```

### 5.2 如果改了压测脚本

执行 Bash 静态语法检查：

```bash
cd /Users/ling/sub2api/docs/test/claude-oauth-soak-24h

bash -n run_24h.sh send_turn.sh cache_hit_demo.sh \
  parse_anthropic_sse.sh usage_guard.sh \
  init_session_identities.sh verify_session_identities.sh \
  summarize.sh test_cache_hit_demo.sh test_run_24h.sh \
  test_send_turn.sh lib/runtime.sh sessions/*.sh
```

这条命令成功时通常什么都不显示。

然后运行不会访问真实 sub2api 或 Anthropic 的模拟测试：

```bash
./test_send_turn.sh
./test_cache_hit_demo.sh
./test_run_24h.sh
```

正常应该分别显示：

```text
send_turn response validation tests passed
cache hit confirmation demo tests passed
single-session 30-request confirmation runner tests passed
```

如果任意一个测试失败，不要推送。

### 5.3 如果后端和压测脚本都改了

上面两组测试都要执行。

## 6. 本机第四步：只暂存本次要同步的文件

先回到仓库根目录：

```bash
cd /Users/ling/sub2api
```

不要执行：

```bash
git add .
```

应该明确写出文件或目录。例如本次修改后端 gate、Compose 和压测 runner，可以执行：

```bash
git add \
  backend/internal/service/gateway_claude_oauth_companion.go \
  backend/internal/service/gateway_forward.go \
  backend/internal/service/gateway_service.go \
  backend/internal/service/gateway_claude_upstream_approval.go \
  backend/internal/service/gateway_claude_upstream_approval_test.go \
  deploy/docker-compose.yml \
  deploy/docker-compose.local.yml \
  deploy/docker-compose.dev.yml \
  deploy/docker-compose.standalone.yml \
  docs/test/claude-oauth-soak-24h
```

如果以后只改了一个脚本，例如 `send_turn.sh`，就只暂存它：

```bash
git add docs/test/claude-oauth-soak-24h/send_turn.sh
```

暂存后检查：

```bash
git status --short
git diff --cached --check
git diff --cached --stat
```

成功标准：

- `git diff --cached --check` 没有输出；
- `git diff --cached --stat` 只列出本次要提交的文件；
- 没有 `.env`、API key、OAuth token、抓包或运行日志。

如果暂存错了某个文件，可以只把它从暂存区拿出来，不删除本地修改：

```bash
git restore --staged 路径/文件名
```

## 7. 本机第五步：创建 commit

根据实际修改写 commit 信息。

例如后端和 runner 一起修改：

```bash
git commit -m "test: approve final Claude upstream requests"
```

例如只修改压测脚本：

```bash
git commit -m "test: update Claude OAuth soak runner"
```

成功后会显示 commit 摘要。

查看刚创建的 commit：

```bash
git log -1 --oneline
```

把输出中的 commit SHA 记住。例如：

```text
abc1234 test: update Claude OAuth soak runner
```

服务器拉取后要用这个 SHA 核对是不是同一版。

---

## 8. 本机第六步：推送到自己的 Fork

执行：

```bash
git push myfork codex/claude-request-alignment
```

这里必须是 `myfork`，不要写本机的 `origin`。

原因：

- 本机 `myfork` 指向 `https://github.com/ljl55586/sub2api.git`；
- 本机 `origin` 指向官方仓库 `Wei-Shaw/sub2api`；
- 当前开发分支应该推到自己的 Fork。

推送完成后检查：

```bash
git status --short --branch
```

正常应该显示当前分支与：

```text
myfork/codex/claude-request-alignment
```

同步，并且没有 `ahead` 提示。

注意：工作区仍可能存在其他未提交文件。这不代表本次 push 失败，只要刚才 commit 的文件已经推送即可。

# 第二部分：服务器如何拉取相同版本

## 9. 服务器第一步：先停止旧压测

这一部分在服务器执行。

先查看是否有旧 runner：

```bash
pgrep -af '[r]un_24h.sh' || echo '当前没有正在运行的压测'
```

再找到最近一次运行目录：

```bash
latest_run_dir=$(
  ls -dt /root/sub2api-soak-runs/run-* 2>/dev/null |
    head -n 1 || true
)
printf 'latest run: %s\n' "$latest_run_dir"
```

如果存在旧运行目录，先请求优雅停止：

```bash
if [[ -n $latest_run_dir ]]; then
  touch "$latest_run_dir/control/STOP"
fi
```

`STOP` 的作用是：阻止 runner 继续创建下一条请求。

### 如果 runner 正停在 `SEND REQUEST` 确认界面

此时它正在等待键盘输入，单独创建 `STOP` 文件不会立即让 `read` 返回。

进入旧 tmux：

```bash
tmux attach -t sub2api-soak
```

然后按：

```text
Ctrl-C
```

当前 approval stage 会被 reject，runner 退出。

从 tmux 脱离但不结束里面的程序：

```text
先按 Ctrl-b，松开，再按 d
```

最后再次确认 runner 已停止：

```bash
pgrep -af '[r]un_24h.sh' || echo '旧压测已经停止'
```

只有看到“旧压测已经停止”后，才继续拉取新代码。

---

## 10. 服务器第二步：进入源码目录并检查是否有脏文件

执行：

```bash
cd /root/sub2api-src
git status --short --branch
```

理想情况：服务器源码目录没有本地修改。

如果出现 `M` 或 `??`：

- 先不要 pull；
- 不要运行 `git reset --hard`；
- 不要直接删除文件；
- 先确认这些修改是谁留下的、是否需要保存。

服务器源码目录应该只用于拉取和构建，不建议直接在服务器上改代码。

---

## 11. 服务器第三步：确认 `myfork` 远端

执行：

```bash
git remote -v
```

如果已经存在：

```text
myfork  https://github.com/ljl55586/sub2api.git
```

可以直接继续。

如果没有 `myfork`，添加它：

```bash
git remote add myfork https://github.com/ljl55586/sub2api.git
```

再次确认：

```bash
git remote get-url myfork
```

必须输出：

```text
https://github.com/ljl55586/sub2api.git
```

使用 `myfork` 的好处是：无论服务器的 `origin` 当前指向官方仓库还是 Fork，本文命令都不会拉错。

---

## 12. 服务器第四步：拉取指定分支

先从 Fork 获取最新提交：

```bash
git fetch myfork
```

切换到开发分支：

```bash
git switch codex/claude-request-alignment
```

如果服务器第一次使用这个分支，上一条命令提示分支不存在，则执行：

```bash
git switch -c codex/claude-request-alignment \
  --track myfork/codex/claude-request-alignment
```

然后进行只允许快进的拉取：

```bash
git pull --ff-only myfork codex/claude-request-alignment
```

`--ff-only` 的作用是防止服务器自动生成一个意外的 merge commit。

检查服务器当前版本：

```bash
git log -1 --oneline
git status --short --branch
```

`git log -1 --oneline` 的 SHA 应该和本机第 7 步记下的 commit SHA 一致。

如果 SHA 不一致，不要 build，也不要开始压测。

# 第三部分：改了 sub2api 后端源码时怎么部署

## 13. 什么时候必须重新 build 镜像

以下内容发生变化时，必须重新 build：

- `backend/**/*.go`；
- `backend/go.mod` 或 `backend/go.sum`；
- `frontend/**`；
- `Dockerfile`；
- 构建过程会打进镜像的其他源码。

只改以下内容时不需要 build：

- 压测脚本；
- prompt；
- schedule；
- README；
- `/root/sub2api-deploy/.env`；
- 仅 Compose 环境配置。

---

## 14. 服务器：重新 build sub2api 镜像

确认当前目录是源码目录：

```bash
cd /root/sub2api-src
git log -1 --oneline
```

开始构建：

```bash
docker build -t weishaw/sub2api:latest .
```

这一步是把刚刚 pull 下来的源码编译进新的 Docker 镜像。

成功标志：

- 命令退出码为 0；
- 最后显示镜像成功构建；
- 没有红色错误。

如果 build 失败：

- 不要重建当前正在运行的容器；
- 旧 sub2api 仍然可以继续运行；
- 先处理 build 错误。

---

## 15. 如果 Compose 模板也变了，不要盲目覆盖部署文件

源码模板位于：

```text
/root/sub2api-src/deploy/
```

实际服务器使用的是：

```text
/root/sub2api-deploy/docker-compose.yml
```

部署文件可能包含服务器自己的端口、卷和环境配置，所以不要直接无脑复制覆盖。

先比较：

```bash
diff -u \
  /root/sub2api-deploy/docker-compose.yml \
  /root/sub2api-src/deploy/docker-compose.local.yml |
  less
```

只把本次真正需要的配置手工合并到：

```text
/root/sub2api-deploy/docker-compose.yml
```

修改前可以先做一个备份：

```bash
cd /root/sub2api-deploy
cp docker-compose.yml \
  "docker-compose.yml.backup-$(date -u +%Y%m%dT%H%M%SZ)"
```

修改后检查 Compose 语法：

```bash
docker compose config -q
```

成功时没有输出。

对于最终上游 approval gate，sub2api 服务必须包含：

```yaml
- SUB2API_UPSTREAM_APPROVAL_DIR=${SUB2API_UPSTREAM_APPROVAL_DIR:-}
- SUB2API_UPSTREAM_APPROVAL_TOKEN=${SUB2API_UPSTREAM_APPROVAL_TOKEN:-}
```

并且 `.env` 中要有：

```text
SUB2API_UPSTREAM_APPROVAL_DIR=/app/data/upstream-approval
SUB2API_UPSTREAM_APPROVAL_TOKEN=一段随机密钥
```

绝对不要把 `.env` 提交进 Git。

---

## 16. 服务器：只重建 sub2api 应用容器

进入部署目录：

```bash
cd /root/sub2api-deploy
```

先检查 Compose：

```bash
docker compose config -q
```

然后只重建 sub2api，不动 PostgreSQL 和 Redis：

```bash
docker compose up -d \
  --no-deps \
  --force-recreate \
  --pull never \
  sub2api
```

参数解释：

- `-d`：后台运行；
- `--no-deps`：不重建 PostgreSQL 和 Redis；
- `--force-recreate`：即使配置看起来没变，也重新创建 sub2api 容器；
- `--pull never`：使用刚刚本地 build 的镜像，不从远端拉旧镜像；
- `sub2api`：只操作应用容器。

检查容器状态：

```bash
docker compose ps
```

检查健康接口：

```bash
curl -fsS http://127.0.0.1:8080/health
printf '\n'
```

查看最近日志：

```bash
docker compose logs --tail=100 sub2api
```

成功标准：

- sub2api 容器是 running/healthy；
- health 请求成功；
- 日志里没有持续 panic、数据库连接失败或 Redis 连接失败。

---

## 17. 服务器：确认 approval gate 配置已进入容器

执行：

```bash
cd /root/sub2api-deploy

docker compose exec -T sub2api sh -c '
  set -e
  test "$SUB2API_UPSTREAM_APPROVAL_DIR" = /app/data/upstream-approval
  test -n "$SUB2API_UPSTREAM_APPROVAL_TOKEN"
'
```

成功时没有输出。

再检查共享目录：

```bash
install -d -m 700 \
  /root/sub2api-deploy/data/upstream-approval

ls -ld /root/sub2api-deploy/data/upstream-approval
```

这个宿主机目录必须对应容器中的：

```text
/app/data/upstream-approval
```

approval token 不要打印到终端，不要发到聊天里，也不要写进压测结果。

# 第四部分：只改了压测脚本时怎么同步

## 18. 只改压测脚本时，服务器需要做什么

本机完成 commit 和 push 后，在服务器执行第 9～12 步：

1. 停止旧 runner；
2. 检查服务器工作区；
3. `git fetch myfork`；
4. `git pull --ff-only`；
5. 核对 commit SHA。

然后执行：

```bash
cd /root/sub2api-src/docs/test/claude-oauth-soak-24h
chmod 700 *.sh sessions/*.sh testdata/fake_curl.sh
```

这一步是确保同步后的脚本仍然可以执行。

只改压测脚本时，不要执行：

```bash
docker build ...
docker compose up ...
```

因为脚本是服务器宿主机直接读取的，不在 sub2api 镜像里。

---

## 19. 服务器：对同步后的压测脚本做静态检查

执行：

```bash
cd /root/sub2api-src/docs/test/claude-oauth-soak-24h

bash -n run_24h.sh send_turn.sh cache_hit_demo.sh \
  parse_anthropic_sse.sh usage_guard.sh \
  init_session_identities.sh verify_session_identities.sh \
  summarize.sh test_cache_hit_demo.sh test_run_24h.sh \
  test_send_turn.sh lib/runtime.sh sessions/*.sh
```

成功时没有输出。

检查 followup 数量：

```bash
jq -e 'all(.[]; length == 29)' prompts/followups.json >/dev/null
```

成功时也没有输出。

---

## 20. 服务器：运行不会访问真实上游的模拟测试

执行：

```bash
./test_send_turn.sh
./test_cache_hit_demo.sh
./test_run_24h.sh
```

这三项使用 fake curl，不会向真实 Anthropic 发送压测请求。

成功标志：

```text
send_turn response validation tests passed
cache hit confirmation demo tests passed
single-session 30-request confirmation runner tests passed
```

任意测试失败，都不要开始正式压测。

## 29.1 无人值守自动批准

已经人工核对过请求结构后，如果要让这一个会话自行完成 30 轮，使用正式的自动批准开关：

```bash
export SOAK_AUTO_APPROVE_UPSTREAM='1'

"/root/sub2api-soak-runs/auto-$(date -u +%Y%m%dT%H%M%SZ)"

```

不要使用：

```bash
yes 'SEND REQUEST' | ./run_24h.sh
```

这种写法把确认文本提前放进公共 stdin，用量检查等子进程可能把文本消费掉，之后 runner 会因确认内容错位而安全停止。

正式自动模式完全不读取 stdin，但仍保留：

- preview 安全检查和 `upstream-previews/` 审计副本；
- 后端 approval gate；
- 首轮 quota → 随机延迟 → title → main 的严格顺序；
- 后续 main-only bundle 检查；
- STOP、24 小时 deadline、5h/7d 用量保护和错误即停。

切回人工确认：

```bash
export SOAK_AUTO_APPROVE_UPSTREAM='0'
```

每次切换模式都必须使用新的 `SOAK_OUTPUT_DIR`，不能继续失败或已经写入状态的旧目录。

## 30. 第一轮应该看到什么

runner 会先把下游请求交给 sub2api。

sub2api 完成最终 CCH、缓存断点、headers 和 body 构造后，会在真正访问 Anthropic 之前暂停。

首轮应该显示：

```text
========== FINAL UPSTREAM REQUEST(S): NOT SENT ==========
bundle: quota,title,main
approved send order: quota -> wait 67s -> title -> main
...
```

`67s` 只是示例。每个新会话会在 `45–90` 秒范围内随机选一个实际值。

然后自动使用 `less` 打开完整 preview。

在 `less` 中：

- 方向键：逐行移动；
- PageUp/PageDown：翻页；
- 按 `/cch=`：搜索 CCH；
- 按 `n`：跳到下一个搜索结果；
- 按 `q`：退出 preview，返回确认提示。

退出后会看到：

```text
Type exactly SEND REQUEST to release this upstream stage:
```

如果确认内容正确，输入：

```text
SEND REQUEST
```

只有完全一致的这两个单词会放行。

首轮只确认一次。确认后不是三个请求并发发送，而是由后端严格执行：

1. 先发送 quota；
2. quota 收到上游响应 headers，或者得到明确的传输错误；
3. 等待终端显示的随机秒数；
4. 发送 title；
5. title 收到上游响应 headers，或者得到明确的传输错误；
6. 最后发送 main。

quota 或 title 失败时仍会继续下一步，不会把 main 永久卡死。

后续每轮应该只显示：

```text
bundle: main
```

每条 main 分别确认。

---

## 31. 什么情况下绝对不要输入 `SEND REQUEST`

出现以下任意情况时，不要批准：

- 首轮不是 `quota,title,main`；
- 后续正常轮次不是 `main`；
- preview 中出现 `network_sent:true`；
- URL 不是 `https://api.anthropic.com/...`；
- CCH 仍然是 `00000`；
- session ID 与预期不一致；
- body 缺少应该存在的历史；
- Authorization 没有显示为 `[redacted]`；
- runner 报告 `invalid or unsafe upstream preview`；
- 用量已经接近或超过安全线。

输入任意其他内容，例如：

```text
DO NOT SEND
```

runner 会写 `.reject`，后端不会访问 Anthropic，并以退出码 `75` 停止当前 run。

停止后不要在旧输出目录继续运行。修复问题后创建新的 `SOAK_OUTPUT_DIR`。
